Minimization algorithm
======================

Input:

* The input to minimize, expressed as a token tree (see
  structure-deduction-algorithm.txt).

* A deterministic, language-dependent function that takes as input a
  node in the token tree and yields an optional non-trivial candidate
  replacement text.  Every node has the empty string as a trivial
  candidate replacement; the non-trivial alternative (if present) is
  only tried after the empty string fails.

* A deterministic acceptance test that takes as input a byte sequence
  and returns a boolean saying if that sequence is accepted.  The
  acceptance test must return true when passed the entire original input
  (halt with error otherwise).

* An optional --max-passes limit on the number of passes.

Output:

* A minimized input byte sequence that passes the acceptance test and is
  approximately 1-minimal.  Exact 1-minimality would mean that for every
  live node in the tree, replacing it (with any candidate replacement)
  results in an input that is not accepted.

* While running, a sequence of acceptance test invocation reports, where
  each report has:

  - The candidate sequence number, starting with 1.  Candidates that
    are identical to previous ones (and hence have memoized verdicts)
    *are* shown and counted.
  - The current last-accepted size of the input, in tokens.
  - A measure of progress, described in detail below.

  and a sequence of acceptance test result reports, each indicating
  whether the corresponding input was accepted and whether the verdict
  was a hit in the memo table.

Rationale: In the output, the size is measured in tokens, partly because
during development I want to see a bit more of the internals, and the
units are somewhat arbitrary anyway.  This choice might be revisited.


Data structures
---------------

`replacement` maps a TTNode instance (using its id() as the key) to
`bytes`.  An absent mapping means the node has not been replaced, while
mapping to a byte sequence means it has been replaced with that
sequence.  Initially all nodes are marked as unreplaced (the map is
empty).  (The replacement is sometimes referred to in this spec as a
"string" for familiarity and concision, but "byte sequence" is what is
technically meant.)

`memoized_accept` is a global memoization table that maps an md5sum of a
candidate byte sequence to either true (accepted) or false (rejected).
(Hits for accepted inputs will be unusual, but can happen in some corner
cases.)


Node size
---------

This algorithm measures the size of a node by the number of live,
original tokens it contains.  A node is "live" if it, and all of its
ancestors, has not been replaced.  The size does *not* depend on which
replacement string is used, and it also does not depend on whether any
whitespace will be inserted to prevent token coalescing during
rendering.


Minimization Algorithm 1 (MA1)
------------------------------

Let S be the number of tokens in the input tree.  (If S=0 then halt
early as there is nothing to do.)

Let G, a rational number, be the target granularity, the number of
tokens we would ideally like to attempt to remove when forming each
candidate.  It is set according to the sequence:

  G = S, S/2, S/4, S/8, ...

Each pass operates with successively smaller G.  The final pass has G in
the range [1,2).  During a given pass, a node is a candidate to be
removed if its size is greater than G/2.  (Some smaller nodes also end
up incidentally being candidates, depending on the context, as explained
below.)  Consequently, the final pass tries to remove all nodes with
size 1, i.e., individual tokens (and groups that only contain one live
token).

The --max-passes option can be used to limit the number of passes, so in
that case the final G may be greater than or equal to 2.

The algorithm core is the recursive function minimize_node, which takes
as input a tree node (and G), and modifies the associated subtree,
killing nodes when doing so results in an accepted candidate input.  The
recursion is started by `minimize_node(root)`.

minimize_node(parent) scans the children of `parent` in reverse order,
ignoring dead (not alive) nodes.  It also skips the delimiters at either
end if `parent` is a delimiter group.  For a given child node N with
size s:

1. If s > G/2, N is large enough to try replacing in its entirety.  Test
   the candidate formed by replacing it with the empty string.  If that
   fails, and it has a non-trivial replacement, try that too.  If either
   succeeds, mark the node as replaced and skip case 2.

2. If s > G, N is so large that we should try replacing its children
   too, so recursively call `minimize_node(N)`.

3. If s <= G/2, N by itself is too small, so it will form the last node
   of a "run".  Continue working backwards, skipping dead nodes and
   accumulating live nodes with size less than or equal to G/2 (*) into
   the run so long as the total size is less than or equal to G.  Once
   the run has been maximally filled or we are out of nodes to add, test
   the candidate formed by replacing the entire run with the empty
   string.  If it succeeds, kill all nodes in the run.  If that fails,
   but the run consists of just N alone, then also try its non-trivial
   replacement if it has one.  Then continue the loop with the next
   sibling in iteration order after the last one in the run.

   (*): This condition ensures that nodes that meet the case 1 condition
        will still be tried on their own.

minimize_node(leaf) should only ever happen if the input contains just
one token.  This case is not important; just return without doing
anything.

If at some point there are no live tokens (which would happen if the
acceptance test just accepted unconditionally, leading to all children
of the root being deleted), terminate the minimization effort early.

Rationale: When s > G, one might be tempted to skip the case 1 test
since we will have already attempted to replace N on a previous pass
with a larger G.  But if we made progress in the meantime, we might have
deleted something that was blocking N from being removed, so trying
again could work.  (And if there was literally no progress in the
meantime, then memoization means this costs basically nothing.)
Persistently trying to remove entire nodes is important because some
constructs, such as C++ function definitions, can be difficult or
impossible to hollow out, even in cases where deleting the entire thing
would work.

Rationale: The reason for going backwards is that we expect the input to
be something like a C++ program, which mostly contains declarations
before references.  Deleting a declaration without deleting its
references is almost always unproductive since typical acceptance tests
require that the input be well-formed.  That said, working backwards is
a very crude way to avoid breaking decl-ref edges, and a possible future
extension is to explicitly compute, represent, and respect such edges.

Discussion: Because we use a hard stop condition when G is less than 2,
this algorithm does not guarantee 1-minimality, despite the requirements
calling for that.  It's of course easy to modify it to keep repeating
the final G until quiescence, but full 1-minimality is more of an
aspirational goal than a hard requirement, and omitting iteration to
quiescence allows for a more meaningful progress report.

Note: On the first pass, G=S, which means no node will satisfy case 2
(since no node's size can be greater than G), and hence the
grandchildren of the root node will not be considered for replacement,
only its direct children will (typically as part of runs).  That is
likely to be the case for the first several passes in fact.

Rationale: It has been suggested to have minimize_node accept a sequence
of nodes instead of just one node so that the root can be processed by
case 1 and hence potentially discarded in its entirety.  In practice,
that is very unlikely to satisfy the acceptance test, and I prefer the
slightly simpler interface of having it accept just one node.


Progress report
---------------

The "completion fraction" of a given candidate is the position of the
last token being considered for replacement within the sequence of live
tokens, measured from the end (since we work backwards).  That is, if
there are L live tokens, and we are testing a candidate that tries
removing a sequence that ends with (1-based) live token E, then the
completion fraction is (L - E) / L.

Rationale: On each pass, the first thing we try is removing a suffix of
the remaining live file.  In that case, E=L, so the first completion
fraction is 0.  Typically, the fraction reaches a maximum (but not
exactly 1) when we try to remove only the very first token of the file.
It increases monotonically (but not strictly) as the algorithm runs; see
proof below.  It's a bit crude as a measure due to the way the algorithm
interleaves testing removal of chunks of various sizes, but also
relatively simple, so should suffice as a first attempt.

There is a corner case to consider though: it is possible for a
candidate to be formed by trying to delete a node, or a run of nodes,
that have no remaining live tokens.  We would expect the attempt to
succeed at the memoization stage, but we run the test machinery anyway
for uniformity.  In that case, let E be 1-based index of the live token
immediately to the left of the first node's subtree, or 0 if there is
none.  That in turn means that the completion fraction could be 1; so be
it.

Prior to testing a candidate, issue a progress report object with
attributes:

  P:  pass number, starting with 1
  Pm: number of passes, floor(log_2(S))+1
  G:  granularity, rounded to the nearest 0.1
  F:  completion fraction as an integer percentage, capped at 99
  R:  sum of sizes of nodes replaced in this candidate

Brief justification of Pm formula: For S=4, G=[4, 2, 1], log_2(S)=2, so
Pm=3, which is right.  For S=5, G=[5, 2.5, 1.25], log_2(S) is about 2.3,
so again Pm=3.

If the --max-passes N option is used, Pm is N if that is smaller than
the formula shown here.

This is rendered as a <status> string as:

  P=($P/$Pm) G=$G F=$F% R=$R

$P is printed with enough leading zeroes to ensure it has the same
number of digits as $Pm.  $G and $R have leading zeroes to keep their
length consistent, taking into account the maximum value of S.  $F is
printed with two digits (which is sufficient due to the cap).

2026-11-01: The output of G is disabled now since it isn't very useful
and causes lines to exceed 80 columns when minimizing large files.

As the minimizer runs, it prints status lines to the console.  Prior to
testing a candidate, it prints:

  N=$N S=$S <status> ...

without printing a trailing newline.  $N is the sequence number of the
candidate being tested, and is padded with leading zeroes so it has at
least 6 digits.  $S is the size of the last-accepted input in tokens,
padded with zeroes so it has the same number of digits as the number of
tokens in the initial input.  (Here, I'm overloading S a little, since
in the algorithm it stays constant, but here it tracks the reduction in
size of the accepted input.)  Note that the size of the candidate being
tested can be calculated as S-R.

When the test completes, print either "rejected" or "ACCEPTED", then
a newline.

In the case of "ACCEPTED", follow it with " (removed N)" where N is the
number of tokens removed (or replaced), i.e., the R number in the
preceding progress report.

If this progress report was issued for a candidate that was not actually
run due to a hit in the memoization table, then write " (memo)" after
the verdict.

  Rationale: Although this contributes a bit of verbiage to the output,
  it also makes it a lot easier to follow what the algorithm is doing
  when I am studying the individual candidates and looking for ways to
  improve its efficiency.  Without it, candidates I expect to see just
  don't appear, and I have to recognize the textual identity myself.

Rationale: The digit padding should keep all fields in consistent
columns in the console output for ease of reading when iterations are
rapid.  As the minimizer runs, N will be increasing, and S decreases
whenever progress is made.  P provides the outer loop progress and F the
inner loop progress, with G and R providing a bit more insight into the
operation of each loop.


Proof that completion fraction increases monotonically
------------------------------------------------------

During a single pass, the completion fraction increases monotonically
(but not strictly) after each attempt.  (It resets to 0 when a new pass
begins.)

When a candidate chunk (node or run of nodes) is not removed, the number
of live tokens L does not change, and due to the way the algorithm is
structured, the next E will either be the same or less, so (L - E) / L
will be nondecreasing.

When a candidate chunk *is* removed, L decreases by s (the chunk size),
and the next E will be at most (E - s).

There are two degenerate cases:

* If s=0 (the case of deleting a node that had no live tokens), the
  fraction does not change.

* If s=L, meaning we deleted the whole file, the minimization loop will
  terminate early, so no more progress reports will be issued.

Setting aside those two cases, we must prove the claim:

  (L - E) / L   <=   ((L - s) - (E - s)) / (L - s)

when 0 < E <= L and 0 < s < L, for integers L, E, and s.

Proof:

  Multiply both sides by both denominators (which are positive):

    (L - E) (L - s)    <=    ((L - s) - (E - s)) L

  Simplify the RHS by canceling -s:

    (L - E) (L - s)    <=    (L - E) L

  Multiply out both sides:

    L**2 - Ls - LE + Es    <=    L**2 - LE

  Cancel like terms:

    -Ls + Es   <=   0

  Divide both sides by (positive) s:

    -L + E  <=  0

  Add L to both sides:

    E  <=  L

  Which is true by the assumption 0 < E <= L.  QED.


Minimization Algorithm 2 (MA2)
------------------------------

MA2 makes as many passes as the maximum depth, MAX_DEPTH, of the token
tree root at `root`.  ("Depth" is defined as the maximum number of edges
from root to leaf, per `token_tree.depth()`.  So a tree with a root
node, all of whose children are leaves, has depth 1.)

If --max-passes N, then regard MAX_DEPTH as at most N.

As pseudocode, the algorithm is:

  For `target_depth` in [1,MAX_DEPTH]:

    Invoke `ma2_min_node(root, target_depth)`.

  def ma2_min_node(node, max_depth):

    Let `children` be the surviving (unreplaced) children of `node`,
    excluding the delimiters if `node` is a delimiter group.

      -> If a child is not marked as replaced, but it has no live tokens
         due to replacements further down, this algorithm still treats
         it as unreplaced for uniformity.

    Set `granularity` to `len(children)` if `node` is a delimiter group,
    and `len(children)//2` otherwise.  Then clamp to at least 1
    (otherwise we'd be in an infinite loop).  This is the number of
    child nodes we are currently trying to remove at once.

      Rationale: For a node that is not a delimiter group, we just tried
      (and failed) to delete it in its entirety in the caller.  The only
      exception is when `node==root`, but trying to delete the whole
      file is very unlikely to succeed.  For a delimiter group, however,
      it might be possible to delete the interior.

    Set `limit` to `len(children)` also.  This is the number of child
    nodes in scope for removal; children beyond the limit are deemed
    (for the duration of this call) necessary for candidate acceptance.

    While `limit` > 0:

      Test a candidate formed by replacing the last `granularity`
      surviving elements of `children` that are not beyond `limit` with
      the empty string.

      If ACCEPT:

        Permanently replace the relevant children (updating what
        `children` refers to).

        Reduce `limit` by the number of replaced children to preserve
        the boundary between doubtful and necessary children.

        Double `granularity`, but then clamp it to `limit`.

      If REJECT and `granularity` > 1:

        Cut `granularity` in half, rounding down.

      If REJECT and `granularity` == 1:

        Let `c` be the child we tried to remove.

        If `c` has a non-trivial replacement:

          Test a candidate formed by replacing `c` with its non-trivial
          replacement.

          If ACCEPT:

            Permanently replace `c` with that replacement.

            Reduce `limit` by 1 to account for the replaced child.

            Keep `granularity` at 1 (since `c` required individualized
            attention, its neighbor might too).

            Continue to the next iteration of the main loop.

        Reduce `limit` by 1.  The relevant child `c` is considered
        "necessary" until we revisit `node` in a later pass.

        If `max_depth` > 1:

          Invoke `ma2_min_node(c, max_depth-1)`.

        Note: `granularity` remains 1.

In cases where a node, or the entire tree, has no live tokens, the
algorithm as specified should naturally work without needing any special
cases.  In particular, I think this algorithm cannot issue a progress
report when L (the number of live tokens in the last-accepted candidate)
is zero.

For this algorithm, we use the same progress report form:

  P:  target_depth
  Pm: MAX_DEPTH
  G:  granularity (which is an integer here) (currently disabled)
  F:  same as above
  R:  same as above

The monotonicity argument for F within a pass still holds.  The new case
is when we enter the recursive call, but in that case the end token of
the next candidate will be no later in the file than the end token of
the previous due to the containment of the child `c` within the parent
`node`.


This algorithm is activated by passing --ma2 to the minimizer program.
For now, MA1 is the default.

Motivation:

  MA2 is motivated by a few observations.  First, if we fail to remove a
  large suffix of the original file, it is almost always a waste of time
  to try removing a large section higher up, since that will nearly
  always break ref-decl edges pointing from the suffix we failed to
  remove into the removed section.  Instead, it is better to immediately
  try to remove less at the end to improve the chance of removing
  something there.  We want to work toward either removing something or
  concluding that a particular top-level construct is necessary as
  quickly as possible, since those are the two most likely ways to make
  progress.  In contrast, MA1 makes many extremely low probability "Hail
  Mary" attempts before again trying something with reasonable success
  probability.

  Then, having eventually decided something near the end is necessary
  (as is typical), we want to repeat that process to zoom in on the next
  necessary top-level construct.

  Each time we find a necessary node, there is a good chance there will
  be a lengthy stretch of stuff to delete before we get to the next, so
  we increase the granularity when a removal is accepted.  Again, we
  want to zoom in on the next boundary between necessary and
  unnecessary.

  Only after having (approximately) reduced the top-level constructs as
  much as possible (in pass 1) should we then dig into their children
  (in pass 2).  And there, we again aggressively try to remove material
  from the end since that is what frees up earlier nodes to be removed.

  In this algorithm, pass N+1 repeats approximately all of the deletion
  attempts made on pass N.  My hope is that progress made in the
  meantime will allow deletions to succeed that previously failed, and
  that if not, the memoization mechanism will be sufficient to avoid
  substantial cost.  Experimentation is needed here; memoization also
  might need optimization, and the decision to issue progress reports
  for memo hits revisited.

  We keep `granularity` at 1 after finding a necessary child because
  "interesting" features tend to cluster together, so there is a good
  chance the next child (going backward) will also be necessary.  If
  not, we will begin increasing `granularity` after the successful
  removal.

  Unlike MA1, MA2 does not use token counts to choose how much to try to
  remove.  My observation is that structure seems to be a better
  predictor of success than size, hence the departure.

  In this spec, the primary MA2 function is called "ma2_min_node" so its
  name is sufficiently distinct from the primary MA1 function.


MA2 --ma2-brace-groups
----------------------

If MA2 is used, and the --ma2-brace-groups option is passed to smin,
then MA2 will exclusively operate on nodes that are either a child of
the root, or are directly contained by a brace-delimited group node.

Specifically, at the point we recursively call `ma2_min_node`:

  If `max_depth` > 1:

    Invoke `ma2_min_node(c, max_depth-1)`.

instead, invoke a new function:

  def get_brace_groups(n: TTNode) -> Iterator[TTNode]:
    """
    If `n` is a brace group, yield it alone.  Otherwise, perform a
    depth-first search of `n`, in right-to-left child order, yielding
    every node that is a descendant of `n`, is a brace-delimited group,
    and does not have a brace-delimited group between it and `n`.
    """
    # details omitted here

and invoke the recursive call on all of the yielded brace groups:

  If `max_depth` > 1:

    For `bg` in `get_brace_groups(c)`:
      Invoke `ma2_min_node(bg, max_depth-1)`.

When --ma2-brace-groups is specified, use an altered definition of
MAX_DEPTH that only counts edges that either (1) connect the root node
to one of its children, or (2) connect a brace group to a child other
than its delimiters.


Brace Group Child Tree (BGCT)
-----------------------------

The "brace group child tree" consists of:

* Every node in the token tree that is any of:

  - The root node.
  - A direct child of the root node.
  - A direct child of a brace-delimited group node (as recognized by the
    `Language.is_brace_group` method), excluding the delimiter tokens
    themselves.

* An edge from BGCT node P (parent) to BGCT node C (child) if, in the
  token tree, P is an ancestor of C, and the path from P to C in the
  token tree does not go through any other BGCT nodes.

  Equivalently (wording suggested by Claude): The BGCT parent of each
  non-root BGCT node C is the nearest proper ancestor of C (in the token
  tree) that is also a BGCT node.

The children of a BGCT node are ordered, as in the token tree, left to
right based on their position in the input file.

For example, if the input is:

  int foo()
  {
    return 0;
  }

  int bar()
  {
    while (1) {
      g();
      h();

      if (1) {
        j();
      }
    }
    return 1;
  }

then, if paragraph grouping is disabled (preventing, e.g., "g();" and
"h();" from being grouped), and head-body grouping is enabled (to, e.g.,
group together "int foo()" with its body), the corresponding BGCT is:

- root node
  - "int foo() ..."
    - "return 0;"
  - "int bar() ..."
    - "while ..."
      - "g();"
      - "h();"
      - "if ..."
        - "j();"
    - "return 1;"
  - the final whitespace-only token

(The BGCT as defined here is intended to define the same set of nodes
that --ma2-brace-groups operates on, but in a way that is less dependent
on the specific algorithm in use.  TODO: Combine their descriptions.)

The BGCT can be divided into "levels", where "level N" is the set of
nodes for which the number of edges from the root to that node is N.
Hence, level 0 is just the root node, level 1 is all of the root's
children, etc.

A BGCT node N may have a "rightmost child's parent brace group", denoted
RCPBG(N).  This requires that N not be the root node, and that it have
at least one child.  In that case, the rightmost child must have a
parent node in the *token tree* that is a brace-delimited group node,
and that is what RCPBG(N) (of type TTNode) refers to.  In the example
above, every node that isn't a root or leaf has as its RCPBG the brace
group that encloses all of its children.

In the context of a minimization algorithm, the BGCT is mutable in the
sense that the minimizer can "replace" a node with a string (by adding
an entry to an auxiliary map), which then makes that node "replaced",
and it and all of its descendants not "live".

Rationale for disabling paragraph grouping: Paragraph grouping was
originally introduced for MA1, which treats each form of grouping about
the same, and uses them as a sort of soft guide for where to put run
boundaries, but would dig inside all of them eventually.  The BGCT is
meant for use with MA3, which tries to focus on braces, and paragraphs
within function bodies would intefere with minimality there since MA3
doesn't have a way to separate them.

Observation: The actual granularity of nodes in the BGCT depends not
only on where the braces are, but where whitespace is too, because it is
defined in terms of the token tree, which itself is computed using the
whitespace-aware structure deduction algorithm (see
structure-deduction-algorithm.txt).  For example, if the file has no
newlines, then every brace group will have children that are all either
single tokens or other brace groups.  The utility of the BGCT thus
depends, to some degree, on the artifact being minimized having
whitespace (newlines, especially) that corresponds to good (productive)
candidate partition boundaries.


Minimization Algorithm 3 (MA3)
------------------------------

MA3 operates on the brace group child tree (BGCT), with paragraph
grouping disabled.

MA3 has two fixed integer input parameters:

* NECESSITY_INCREMENT (default 10): The amount by which to increase
  max_necessity (when that happens is explained below).

* MAX_EXPLORATION_DEPTH (default 4): Maximum value of exploration_depth.

While running, MA3 has two related integer global variables:

* max_necessity: The maximum number of "necessary" nodes to accumulate
  within any given BGCT node.

* exploration_depth: Initially 1, the maximum level of BGCT nodes to
  examine and consider replacing.

Additionally, associated with each BGCT node N is a mutable sequence
necessary(N) that contains the non-replaced children that were, at some
point, tested for possible replacement, but the resulting candidate(s)
were rejected.  Initially, necessary(N) is empty for all N.

Invariant: necessary(N) is always a suffix of the non-replaced children
of N.  (Thus, it can be represented as a "divider" between the necessary
and possibly-unnecessary non-replaced children.)


Algorithm:

  BGCT_Node is a type denoting a node in the BGCT.


  def children(N: BGCT_Node) -> list[BGCT_Node]:
    """
    Return all non-replaced children of N in the BGCT, in left-to-right
    order.
    """
    # Details omitted; see definition of Brace Group Child Tree (BGCT).


  def level(N: BGCT_Node) -> int:
    """
    Return the level of N in the BGCT.
    """
    # Details omitted; see definition of Brace Group Child Tree (BGCT).


  def ma3_min_node(N: BGCT_Node) -> bool:
    """
    Non-recursively minimize N.
    """

    # Granularity, i.e., number of nodes to try removing at once.
    G: int = 1

    While (len(necessary(N)) < len(children(N)) and
           len(necessary(N)) < max_necessity):

      Let CC: list[BGCT_Node] be up to G contiguous non-replaced,
        non-necessary children of N closest to the end of the file.

      Try to replace all nodes in CC:

        If len(CC) > 1 then only attempt the trivial replacement.

        If len(CC) == 1:

          Let C be the node in CC.

          Try these candidates in order, stopping on the first ACCEPT:

            Attempt the trivial replacement of C.

            Attempt a non-trivial replacement, if one exists for C.

            If RCPBG(C) exists and has a non-trivial replacement, then
            try that replacement too.  If that succeeds, add C to
            necessary(N), then proceed to the ACCEPT case.

      If ACCEPT:

        Commit the replacements as permanent.
        Double G if we used a trivial replacement.

      Else (REJECT) if len(CC) > 1:

        G = len(CC) // 2

      Else (REJECT ONE):

        Prepend the one element in CC to necessary(N).

    Return True if `len(necessary(N)) < len(children(N))`, i.e., we hit
    the necessity limit rather than exhausted the children.


  def ma3_min_subtree(N: BGCT_Node) -> bool:
    """
    Recursively minimize N and its necessary children down to the
    exploration depth.
    """

    ma3_min_node(N)

    # The children of `N` are at level `level(N)+1`.  And the recursive
    # call first tries removing `C`'s children (the grandchildren of
    # `N`).  So, only recurse if the grandchildren's level is within the
    # allowed exploration depth.
    If level(N)+2 <= exploration_depth:

      For C in reverse(necessary(N)):

        ma3_min_subtree(C)

    Return True if any `ma3_min_*` call returned True.


  def ma3_min_tree(root: BGCT_Node) -> None:
    """
    Minimize the entire tree, with attention focused on the end of the
    file, attempting to remove nodes in layers, but with gradually
    increasing limits on effort spent per node and how far we search
    from the end.
    """

    Set max_necessity to 0.

    Do:

      # Expand scope, re-try previously rejected replacements.
      max_necessity += NECESSITY_INCREMENT
      Reset all necessary(N) to be empty.

      # Iteratively deepen the candidates for replacement, but (in this
      # loop) do not repeat replacement attempts.
      For exploration_depth in range(1, MAX_EXPLORATION_DEPTH+1):

        # Remove what we can, subject to `max_necessity`, down to
        # `exploration_depth`.
        ma3_min_subtree(root)

    # Stop when the necessity limit is not stopping us at any level.
    While any `ma3_min_subtree` call returned True.


Algorithm motivation:

  The primary motivation is the observation that candidates formed by
  replacements near the end of the file are particularly productive (in
  expectation) because (for input that resembles C++):

  1. They are much more likely to succeed due to having a minimum of
     other nodes that depend on them, such that removal violates
     syntactic or static semantic constraints.

  2. Successful removal then eliminates some constraints on nodes
     higher up, potentially unlocking their removal, and there are many
     such nodes when we remove one near the end.

  Therefore, MA3 tries to keep its focus on that end, only moving toward
  the start of the file as a consequence of removing intervening
  material, or being forced to expand the scope due to not making
  progress otherwise.

  Restricting attention to the BGCT improves the likelihood of syntactic
  validity in languages like C++, and makes it somewhat easier to reason
  about what a sensible MAX_EXPLORATION_DEPTH ought to be.

  Treatment of RCPBG is motivated by noticing (credit to Claude) that,
  without that, non-trivial replacement will virtually never be tried
  since brace groups are only rarely direct children of brace groups
  (and when they are, replacement with ";" is usually futile anyway;
  TODO: decide whether to remove that entirely).  The case where
  non-trivial replacement is really helpful is when the brace group is
  the last part of a syntactic construct, which is what RCPBG tries to
  identify.

  When a node is found to be "necessary", that (in a Bayesian sense)
  reduces the probability that a future removal attempt will be
  accepted; but each successful removal elsewhere after that increases
  the probability that the original node might now be unlocked.
  Resetting necessary(N) where we do is meant to strike a balance
  between retrying too soon and too late.

  MA3 is deliberately meant as a "coarse minimization" algorithm, which
  should make a lot of progress quickly, at the expense of minimality of
  the final result.  It is expected to be optionally followed in
  practice by a "fine minimization" algorithm that will try harder but
  can benefit from a much smaller starting input.


MA3 Progress Reporting
----------------------

Progress is reported using, from the outer loop:

* Pm: Maximum number of outer loop iterations:

    ceil(len(children(root)) / NECESSITY_INCREMENT)

  for the initial tree.  This will often be a large over-estimate.

* P: Iteration count for the outer loop, starting at 1:

    max_necessity / NECESSITY_INCREMENT

  Print with as many digits as Pm.

* RNF: Root necessity fraction:

    len(necessary(root)) / len(children(root))

  This will start at 0 with each outer loop, but can go both up and down
  as it runs.

  Print as a 2-digit percentage (capped 99 if needed).

* ED: exploration_depth

  Print with as many digits as MAX_EXPLORATION_DEPTH has.

From the (0-based) Ith recursive call ma3_min_subtree(N):

* C[I]: 0-based position of C in `reverse(necessary(N))`

  That is, the progress report includes an array C[] that has one
  element per activation frame.

  Print with as many digits as N[I].

* N[I]: len(necessary(N))

  Another array, N[I] acts as the upper bound for C[I].

  Print with as many digits as max_necessity currently has.

  In the full printout, print each C[I] and N[I] like:

    f"C{I}=({C[I]}/{N[I]}"

  where "{I}" is printed without padding digits, and the others are
  padded with zeroes as indicated above.

From ma3_min_node(N):

* LVL: level(N)

  Print with as many digits as MAX_EXPLORATION_DEPTH.

* L_NEC: len(necessary(N))

  Print with as many digits as max_necessity currently has.

* G: G

  Print with at least 3 digits.

This progress report is admittedly a bit of a mess, as the algorithm's
behavior resists an easy notion of progress against a prediction.  This
will probably need to be revised if MA3 turns out to be effective.


MA3 Enablement
--------------

MA3 is enabled by the --ma3 switch to smin.py.  Doing so disables
paragraph grouping during structure deduction.  The --ma3 switch is
incompatible with --ma2 and --hdd.

Although not intended to be used together, it is not an error to combine
--ma3 with --skip-paragraphs (which is redudant), nor with the
SKIP_HEAD_BODY envvar (which could be a useful experiment).


Candidate testing
-----------------

Candidate inputs are tested for acceptance by calling a `test_candidate`
function.  This function first calls `render_candidate`, which takes the
tree root node as input along with a set of candidate-specific node
replacements, and yields a byte sequence.

Then the md5 hash of the rendered text is checked with the memoization
table, short-circuiting the actual test on a hit, but still printing a
status line.  On a miss, the candidate is written to disk, overwriting
the file that originally contained the initial input (which was backed
up before the main algorithm began).  Then the acceptance test program
is run, its result stored in the memoization table, and that result
returned to the invoking routine.

When running the test program, redirect its stdin from the platform
equivalent of /dev/null (so it can't hang due to trying to read user
input), and also redirect its stdout and stderr to the same.  (Later we
might add an option to save that output somewhere.)

When running the test program, set environment variables:

* INPUT: The name of the input file.

* INPUT_BEST: "$INPUT.best".

* SMIN_PROGRESS: The progress report text that is printed to the console
  before each candidate is tested, e.g., "N=000056 S=16 P=(6/7) G=02.1
  F=06% R=07".  For the initial test that is run before the main
  algorithm begins, SMIN_PROGRESS is set to "initial".

* CHANGED_BYTE_RANGE: A string of the form "A-B" where the candidate was
  created by modifying the byte range [A,B) from the most recently
  accepted input.  For the initial test, it is "None".

Rationale: The latter two can be used by "t_accept.py --input-log" to
more easily follow the algorithm steps.

Whenever a new (not memoized) candidate is accepted, copy its contents
to "$INPUT.best.tmp", then atomically move that file to "$INPUT.best".
(Atomic movement means a curious user who cats that file should never
see it in an incomplete state.)

TODO: It would be nice to have a way for the test program to communicate
a short verdict phrase to include in the minimizer console output so
that the different rejection reasons could be observed in real time.


Candidate rendering
-------------------

The input to render_candidate is a token tree with its already
established replacements on TTNode (which describe the most recently
accepted state), along with a map from TTNode to byte sequence of
additional candidate node replacements to test.  The output is a byte
sequence.

Conceptually, every candidate can be expressed as a candidate token map
CTM from original token (identified by its index, for example) to either
None (meaning the token is live) or a replacement text.  Naively, the
candidate byte sequence is then obtained by concatenating all live
tokens and all replacements in original token order.

For the purpose of rendering a token *tree* (not a flat list), the
complication is that replacement is expressed on TTNode, which includes
interior nodes.  Therefore, when an interior node N has a replacement,
that is expressed in the CTM by saying that the first token T in its
original span is associated with N's replacement text, and all others in
the span have *empty* replacement text.  (In general, the replacements
in the CTM will be different from the leaf node replacements in the
token tree.  Also note that a replacement in an ancestor node
effectively overrides any replacements in descendant nodes.)

For example, if we have "int foo() {...} int x;" and the "{...}" is
replaced by ";", then CTM associates the original token "{" with ";" as
its replacement, and all tokens in "...}" with empty replacements.

Now we can describe how to render a candidate byte sequence from a flat
token list and a CTM.  A contiguous sequence of live tokens is simply
rendered as the concatenation of their original texts.  Suppose we have
a gap in the live tokens:

  ..., A, D1, D2, ..., Dn, B, ...

where A and B are live tokens and all Di are dead, with replacements Ri
in the CTM.

We want to ensure each emitted token (B) or non-trivial replacement (Ri)
appears on a line that has the same indentation as the line that
originally contained that token or the token it replaces (RULE: preserve
indentation), and furthermore not on the same line as a token it was
originally on a different line from (RULE: don't join lines).

Let trail_indent(s: str) -> str be the last newline in s followed by
whatever contiguous whitespace immediately follows it in s, or the empty
string if s does not contain a newline.  This captures the line
indentation of any text following s.

Let leading_ws(s: str) -> str be the contiguous leading whitespace in s.
This is needed to separate the indentation that was present in a deleted
token from possible later newlines in that same token (which are not
relevant due to the deletion).

Let DD[x,y] be the concatenation of Dx through Dy (inclusive).

Partition the sequence D1, D2, ..., Dn, B into "pieces", where each
piece ends with either a dead token with a non-trivial replacement, or B
itself, and every other element in the piece is a dead token with a
trivial replacement.  Each piece corresponds to some non-whitespace to
emit, for which we need to decide what whitespace precedes it.

For each piece Di, Di+1, ..., Dj containing only dead tokens, emit:

  trail_indent(DD[i,j-1] + leading_ws(Dj)) + Rj

This ensures that Rj will be emitted with the same indentation that Dj
had if it is emitted onto a new line.  But (due to using leading_ws) we
do not get fooled by a newline that might appear later inside Dj (say,
in a block comment) and hence should not be considered as part of its
indentation.

For the last piece Di, Di+1, ..., Dj-1, B:

* If leading_ws(B) contains a newline, then emit it in the obvious way.
  (It already contains its own indentation.)

* Otherwise, if trail_indent(DD[i,j-1]) is not empty, emit:

    trail_indent(DD[i,j-1]) + without_leading_ws(B)

  where without_leading_ws(s: str) -> str returns s without the portion
  that leading_ws would return.

  This preserves the indentation leading up to B, and then removes any
  leading horizontal whitespace it might have, so that indentation is
  not disrupted.

* Otherwise, if B does not have any leading whitespace, emit:

    " " + B

  in order to ensure that it does not coalesce with A (RULE: don't
  coalesce tokens).  This rule is conservative, adding spaces in cases
  that might not need them; I accept that imprecision in exchange for
  simplicity and less direct dependence on the input file language
  rules.

* Otherwise, simply emit:

    B

  This is the case where A and B were originally on the same line, and
  will remain so, and B already has whitespace to keep them separate.

Rationale / limitation: The anti-coalescence rule above is only applied
to the final piece, not to non-trivial replacement texts, even though in
general those could coalesce too.  Currently, the only replacement text
I'm planning to use is ";", which will never coalesce (in C++), and I'd
rather not add an extra space before it for aesthetic reasons.  This
rule will need to be revisited if/when other replacements become
possible.

Now let's consider token gaps at the ends.  At the end of the file, we
have:

  A, Di, ..., Dj

Follow the same procedure to partition the sequence into pieces and
render them as such, except that there is no B, so the last piece
contains only deleted tokens with trivial replacements, so can be
entirely discarded.

At the start of the file, we have:

  Di, ..., Dj, B

Again, partition into pieces and render as before, except that the rule
that prepends a space to B is not needed since nothing (that can
potentially coalesce, given the assumption of non-coalescing
replacements) is emitted before it.

At the very end, if the initial input file ended with a newline, but the
current candidate does not, add one.  (It's somewhat easy for the
algorithm to drop final newlines, but doing so causes needless annoyance
when debugging smin.)

Implementation note: The algorithm description here, involving building
a CTM and then operating on the flat token sequence, is primarily
intended for expositional clarity.  The implementation is free to
reorganize the computation for efficiency.  That said, my intent is to
start with a naive implementation that closely follows the spec in order
to validate that spec and to provide a reference implementation that a
more optimized implementation could be tested against.


Startup
-------

Start by reading the input <fname> and building a token tree from it
using C++ language rules.  (Later we might add more languages, and an
option to choose the language.)  Halt with an error if <fname> cannot be
read.

Summarize the initial input on one line:

  Initial <fname> has <S> tokens, <bytes> bytes, and a maximum tree
  depth of <depth>.

Then, as a sanity check, render the initial tree as a byte sequence in
memory and verify it exactly matches the contents of <fname> (halt with
internal error otherwise).

Next, run the test program.  First print (without a newline, but
flushing the output):

  Checking <program> on initial <fname> ...

Then if the test passes, print "accepted\n", otherwise "REJECTED\n".
In the latter case, halt with:

  Stopping because the initial input was rejected.

Next, make a backup of the input file, with the name of the backup being
"<fname>.bak", overwriting an older backup if one is present.  Print a
message:

  Copied <fname> to <fname>.bak.

or:

  Copied <fname> to <fname>.bak (which was overwritten).

depending on which is applicable.

Also copy the input file to "<fname>.best", and print:

  Will continuously update <fname>.best.

or:

  Will continuously update <fname>.best (which was overwritten).

Initialize the memoization table to record the acceptance of the initial
input.  Then proceed with the minimization algorithm specified above.

Just for specificity: This initial test is *not* counted toward the
attempt numbering in the progress reports.  Those start at 1.


Termination
-----------

At the end of the final pass, the original input file is overwritten
with the rendering of the current tree (with no candidate
substitutions), and a final message printed (on two lines; the first is
wrapped only for exposition here):

  Reduced file <fname> from <orig S> tokens (<orig size> bytes)
  to <S> tokens (<size> bytes).
  Elapsed time (D:HH:MM:SS): <days>:<hours>:<mins>:<secs>

This also happens in response to Ctrl-C.  Note that when Ctrl-C is
pressed, the test program will almost certainly be running, so the
minimizer needs to recognize when the test program terminated for that
reason (as opposed to an ordinary rejection).  Among other things, when
the test terminates this way, the memoization table is not updated.

The minimizer needs to also correctly handle Ctrl-C that is pressed
while it is doing its own work (and potentially modifying its data
structures) to ensure that what is left on disk is a recent input that
was accepted by the test.

When stopping due to Ctrl-C, the above final message is preceded by:

  Stopping early due to Ctrl-C.

When a test is interrupted by Ctrl-C, print its status as "INTERRUPTED"
rather than "accepted" or "rejected".

The driver accepts a --max-seconds command line argument.  After each
candidate acceptance test, if the specified time limit is reached
without normal termination, then stop minimizing, overwrite the input
file with the last accepted input (which might be the one just tested),
and (after printing the "Reduced file ..." and "Elapsed time ..." lines)
print:

  Stopping early due to --max-seconds <S>.

where <S> is the specified limit.
