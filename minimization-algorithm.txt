Minimization algorithm
======================

Input:

* The input to minimize, expressed as a token tree (see
  structure-deduction-algorithm.txt).

* A deterministic, language-dependent function that takes as input a
  node in the token tree and yields a possibly-empty sequence of
  non-trivial candidate replacements that (notionally) make the input
  smaller.  Each replacement is a (possibly empty) byte sequence.
  Implicitly, every node has the empty string as a trivial candidate
  replacement; the non-trivial alternatives are only tried after the
  empty string fails.

* A deterministic acceptance test that takes as input a byte sequence
  and returns a boolean saying if that sequence is accepted.  The
  acceptance test must return true when passed the entire original input
  (halt with error otherwise).

Output:

* A minimized input byte sequence that passes the acceptance test and is
  1-minimal, meaning that for every node in the tree that has not been
  replaced (or had an ancestor node replaced), using any of its
  replacements results in an input that is not accepted.

* While running, a sequence of acceptance test invocation reports, where
  each report has:

  - The test program invocation sequence number, starting with 1.
  - The size of the input being tested in bytes.
  - A measure of progress, described in detail below.

  and a sequence of acceptance test result reports, each indicating
  whether the corresponding input was accepted.


Simplifying assumptions
-----------------------

All nodes have the trivial candidate replacement of the empty string,
which is what gets tried first.  Some (in practice, just brace pairs,
with the candidate ";") have non-trivial candidates.


Definitions
-----------

The "level" of a node is its distance from the root.  The root node is
level 0, its children are level 1, etc.


Data structures
---------------

TTNode is augmented with a new mutable `replacement` attribute of type
`Optional[str]`.  None means the node is "alive", while a string means
it is "dead", having been replaced with that string.  Initially all
nodes are marked as live.

`memoized_accept` is a global memoization table that maps an md5sum of a
candidate byte sequence to either true (accepted) or false (rejected).
(In practice, it will be at most very rare to get a hit for a previously
accepted input, since it means a subsequent "smaller" candidate was
textually identical, but acceptance is tracked for symmetry and possible
occasional utility.)


Algorithm loops
---------------

The core algorithm consists of these functions, which form a series of
nested loops:

minimize_tree (the outermost) iterates `level_limit`, starting at 1 and
counting upward with each iteration.  It does not have an upper limit.
Instead, minimize_tree terminates when an iteration fails to make any
progress (no smaller input is found that is accepted).

minimize_limited_tree iterates `level`, starting at 1 and going up to
and including `level_limit`.

minimize_at_level iterates `parent` over all tree nodes whose level
equals `level-1`, working from the end of the tree.  That is, it
iterates over the parents of the nodes that exist at `level`.  For
progress reporting purposes, it first counts the number of parent nodes,
and identifies `parent` by its index in that sequence.

minimize_node operates on the `parent` node, trying to discard some of
its `N` surviving non-delimiter children.  It first iterates `exponent`
from 0 up to and including `max_exp = ceil(log_2(N))`.  During each
iteration, it partitions the surviving non-delimiter children into
`num_chunks = min(2**exponent,N)` approximately equal-sized chunks and
calls minimize_chunked_node.  It then calls minimize_alt_children.

Rationale: We do not want to try removing delimiters since that will
almost always produce malformed input.  An entire delimiter group can be
removed, however, and this prodedure *will* try emptying such a group by
removing all of its non-delimiter children.

minimize_chunked_node iterates `chunk_index` from 0 to `num_chunks-1`.
During each iteration, it tests a candidate input consisting of the
surviving text outside `parent`, and the surviving children of `parent`
except for those in the indicated chunk, which are replaced with the
empty string.  If the candidate is accepted then all of the nodes in
the chunk are updated to be `replaced` by the empty string.

minimize_alt_children is called by minimize_node.  It iterates over
every surviving `child` node of `parent` that has at least one
non-trivial alternative.

minimize_alts_of_child iterates `alternative` over the non-trivial
alternatives of `child`.  During an iteration, it tests the candidate
formed by replacing `child` with `alternative`.  If that succeeds,
`child` is marked as dead, permanently replaced by `alternative`;
further alternatives for the same `child` are not considered.

Summarizing, the call structure is:

  name                               iter var      num iterations
  --------------------------------   --------      --------------
  minimize_tree                      level_limit   unlimited (by default)
    minimize_limited_tree            level         `level_limit`
      minimize_at_level              parent index  num nodes at `level-1`
        minimize_node                exponent      max_exp+1
          minimize_chunked_node      chunk_index   num_chunks
          minimize_alt_children      child         num children
            minimize_alts_of_child   alternative   num alternatives

Each function returns a boolean, with true meaning it was able to kill
at least one node.  The outer minimize_tree loop halts when
minimize_limited_tree returns false.


Progress report
---------------

Prior to testing a candidate in minimize_chunked_node, issue a progress
report object with attributes:

  M:  level_limit
  L:  level
  P:  parent index + 1
  Pm: num nodes at level
  E:  exponent + 1
  Em: max_exp + 2
  C:  chunk_index + 1
  Cm: num_chunks

This is rendered as a string as:

  M=$M L=($L/$M) P=($P/$Pm) E=($E/$Em) C=($C/$Cm)

Each of the numerators is printed with enough leading zeroes to ensure
it has the same number of digits as the corresponding denominator.

As the minimizer runs, it prints status lines to the console.  Prior to
testing a candidate, it prints:

  N=$N S=$S <status> ...

without printing a trailing newline.  $N is the sequence number of the
candidate being tested, and is padded with leading zeroes so it has at
least 6 digits.  $S is the size of the candidate in bytes, padded with
zeroes so it has the same number of digits as the original input file
size.

When the test completes, print either "rejected" or "ACCEPTED", then
a newline.


Candidate testing
-----------------

In minimize_chunked_node and minimize_alts_of_child, candidate inputs
are tested for acceptance by calling a `test_candidate` function.  This
function first calls `render_candidate`, which takes the tree root node
as input along with a node reference and the text to substitute for that
node.  It renders the complete candidate by walking the tree from the
root, using the substituted text for the specified node, and otherwise
rendering the nodes according to their `replacement` status.

Then the md5 hash of the rendered text is checked with the memoization
table, short-circuiting the actual test on a hit.  On a miss, the
candidate is written to disk, overwriting the file that originally
contained the initial input (which was backed up before the main
algorithm began).  Then the acceptance test program is run, its
result stored in the memoization table, and that result returned to
the invoking routine.


Candidate rendering
-------------------

The rendering procedure takes as input the root TTNode, a node to
replace, and that node's replacement byte sequence.  The tree is then
rendered recursively.

To render a node, concatenate the rendering of its live children and the
replacement text of dead children.  Whenever two non-empty subtree
renderings are joined, and there is no whitespace adjacent to the join
spot on either side, and at least one side's adjacent character has been
affected by replacement, insert one extra space between them (to ensure
that adjacent tokens do not inadvertently coalesce when fed to the
acceptance test).
