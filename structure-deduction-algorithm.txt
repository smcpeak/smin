Structure deduction algorithm
=============================

Input:

* The input file, treated as a sequence of bytes.

* A language-specific tokenization procedure.

* Language-specific delimiter pairing rules.

Output:

* A token tree that heuristically describes the hierarchical structure
  of the input.

    A token is a contiguous sequence of bytes.  The tokens partition the
    input file, such that their concatenation yields the original input
    file.

    A token tree node is either a token or a group.  A group is a
    sequence of child nodes.  Left-to-right traversal of the tree yields
    the original sequence of tokens.


Phase 1: Tokenization
---------------------

The tokenization phase partitions the input into tokens.  The exact
procedure is a parameter that can be tailored to the input language
(e.g., C++ vs. Python).

The most important tokens are delimiters such as braces and parentheses,
as these are treated specially by the deduction algorithm.

Other tokens may include string literals, comments, preprocessor
directives, other kinds of literals, identifiers, etc.

Linguistically insignificant whitespace is included with its following
non-whitespace token, except at the end of the file, which may have a
token containing only whitespace.

Definition: For every token, its "line indentation" is the number of
leading spaces or tabs or other non-newline whitespace (for now, we
treat them all as equivalent for simplicity) on its line (the line with
the first non-whitespace character).  Consequently, all tokens that
begin on a given line have the same line indentation.  The line
indentation of a group is the line indentation of its leftmost token.
If a token is entirely whitespace, then its line indentation is computed
as if it had a non-whitespace character appended.

Rationale detail: The form feed character (0xC) is sometimes used in the
GNU coding style, but is (per that style) supposed to always be followed
by a newline, so counting it as "indentation" shouldn't cause any
problems (even after the much larger issue of proper treatment of tabs
has been resolved).

Definition: A token is "first on its line" if there are no
non-whitespace characters before the token, on the same line.
Similarly, a token is "last on its line" if no non-whitespace characters
follow, on the same line as its last character.

The EOF WS token, if present, is considered "first on its line" if it
has a newline character, but not "last on its line" in any case.


Phase 2: Grouping by delimiters
-------------------------------

The delimiter phase walks the token sequence, maintaining a stack of
unmatched opening delimiter tokens.  When a closing delimiter is
encountered that is not the first token on its line, if the top of the
stack is the corresponding opening delimiter, then a new group node is
created that has the delimiter tokens at either end and the nodes
(including previously created delimiter groups) describing the enclosed
text between them.

If the top of the stack does not correspond, then we search the stack
(in top down order) for a corresponding opening delimiter whose line
indentation is the same as that of the closing delimiter.  If one is
found, then we pop all intervening opening delimiters (hence, they will
not be the start of any group) and form a new group with the found
opening delimiter.  Otherwise, the closing delimiter is skipped, hence
treated as a non-delimiter token.

For a closing delimiter that *is* first on its line, pair it with the
closest opening delimiter of the appropriate kind whose line indentation
matches that of the closer, if one exists.  Otherwise use the same
procedure as for closing delimiters that are not first on their line.

Rationale: The special rule for line-first closing delimiters is meant
to handle a case like:

  void f() {
  #if A
    if (a) {
  #else
    if (b) {
  #endif
      x();
    }
  }

where we want to ensure the final '}' goes with the initial '{', not the
one in the middle.

If the delimiter stack is not empty when the end of file is reached, the
unpaired openers become ordinary tokens.

In subsequent phases, the delimiter tokens at either end of a delimiter
group are excluded from being placed into smaller groups.


Phase 3: Grouping lines
-----------------------

Every node (excluding delimiter tokens) that is the first on its line
(its leftmost token is the first on its line) is grouped with the next
sibling node (excluding delimiter tokens) that is last on its line (its
rightmost token is the last on its line) and all intervening nodes, if
one exists.  This will group ordinary one-line statements together.

It will also group multi-line function definitions if the body is
enclosed by a delimiter and the opening delimiter is on the same line as
the header.  (If not, head and body may still get grouped in phase 5,
and if not, I accept the waste caused by fruitlessly trying to separate
them, in exchange for deduction algorithm simplicity.)


Phase 4: Grouping by indentation
--------------------------------

For every node (excluding delimiter tokens) that is the first on its
line, group it with all following siblings up to but not including the
next sibling that is either (1) first on its line and has equal or less
line indentation, or (2) is the closing delimiter for the group the node
is (directly) in.

Discussion: This rule has potential problems with preprocessor
directives and comments that do not respect the indentation of the
surrounding code.  For now, I accept this potential deficiency.


Phase 5: Grouping paragraphs
----------------------------

A "paragraph" is a contiguous sequence of nodes (excluding delimiter
tokens) that are all first on their line, have the same line
indentation, and do not have any intervening blank lines.  (Per this
definition, blank lines *inside* a group node do not break a paragraph.)
Group all paragraphs.

Assuming all whitespace is associated with the next token (except at
EOF), intervening blank lines can be recognized by observing a node
whose first token has multiple newline characters in its leading
whitespace.


Phase 6: Collapsing redundant groups
------------------------------------

Any group that only has one child is replaced by that child.
Consequently, afterward, every group will have at least two children.
(Empty groups are never created, except possibly in the case of an input
file that is completely empty, depending on what the tokenizer does with
that.)



Examples
========

In these example outputs, the token tree is denoted by enclosing groups
in brackets and tokens as quoted strings.  Quoted strings use C-style
escape rules to denote embedded quotes, etc.  To reduce uninteresting
clutter, some of the quoted strings combine multiple tokens that would
be separated in the real tree.


Input 1: C++ Hello World

  #include <iostream>        // std::cout

  int main(int argc, char **argv)
  {
    std::cout << "Hello\n";
    return 0;
  }

      [

          ]

            "\n  return 0;"
          ]
        ]
        "\n}"
      ]
      "\n"
    ]
  ]

      getNamedParentDeclOpt_templateAdjustment(dn.m_decl);
    if (!parent) {
      // The parent is the TU.

    return true;

Input 3: Python function

  def topo_sort_sccs(
    graph: Dict[str, List[str]], sccs: List[List[str]]
  ) -> List[List[str]]:
    """Topologically sort SCCs."""

    # Map from a node to the index in `sccs` where that node is found.
    # Assumes that each node appears in exactly one SCC.
    node_to_scc: Dict[str, int] = {}
    for i, comp in enumerate(sccs):
      for n in comp:
        node_to_scc[n] = i
