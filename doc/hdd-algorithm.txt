Hierarchical Delta Debugging (HDD) Algorithm
--------------------------------------------

This is a specification of HDD for implementation within smin.


Background
----------

HDD is described in the paper:

  Ghassan Misherghi and Zhendong Su.  "HDD: Hierarchical Delta
  Debugging."  ICSE 2006, pp. 142-151.
  https://www.cs.ucdavis.edu/~su/publications/icse06-hdd.pdf

In that paper, Algorithm 1 contains the HDD pseudocode.  Translated to
pseudo-Python, it is:

  def HDD(input_tree):
    level = 0
    nodes = TagNodes(input_tree, level)

    while nodes is not empty:
      # Apply classic delta-debug flat list minimization.
      minconfig = ddmin(nodes)

      # Update the tree accordingly.
      prune(input_tree, level, minconfig)

      level += 1
      nodes = TagNodes(input_tree, level)

The text explains that TagNodes gathers all of the nodes on a given
level in the tree into a single list for minimization by ddmin.  I think
"tagging" simply means having a means to associate the elements of the
flat list with the tree nodes they came from.


Algorithm within smin
---------------------

Let's elaborate this for use with the smin token tree:

  def nodes_at_level(root: TTNode, level: int) -> list[TTNode]:
    """
    Return a list containing every live node (i.e., it is not replaced,
    and no ancestor is replaced) at the specified level, where 0 means
    the root node, 1 means the root's children, etc., in left to right
    order; except that delimiter tokens at that level are *not*
    included, so we don't try removing them while working at their
    level.
    """
    # details omitted here

  def ddmin(nodes: list[TTNode]) -> None:
    """
    Minimize `nodes` w.r.t. the (implicit) acceptance check using an
    approximation of the classic delta debugging algorithm.  (See
    hdd-algorithm.txt.)

    The elements of `nodes` do not necessarily have the same parent, and
    those with the same parent are not necessarily contiguous because
    they do not contain nodes that have already been replaced by a
    previous pass.
    """

    # Current granularity.  We start by trying to delete about half of
    # the input.
    G: int = max(1, len(nodes) // 2)

    while G > 0:
      runs: list[list[TTNode]] = partition surviving `nodes` into runs
        of length G, with a possibly shorter run last

      for run in reverse(runs):
        candidate = tree where every node in `run` is replaced by the
          empty string
        if candidate is accepted:
          permanently mark all nodes in `run` as replaced (by empty)
          continue

        if (G = 1 and
            the one node `N` in `run` has a non-trivial candidate replacement):
          candidate = tree where `N` is replaced by its non-trivial
            replacement
          if candidate is accepted:
            permanently mark `N` as replaced by its non-trivial
              replacement

      G //= 2

  def hdd_minimize(root: TTNode) -> None:
    """
    Apply an approximation of HDD to tree rooted at `root`, modifying
    its replacement mapping (smin `cur_replacement` map).

    See hdd-algorithm.txt for details on how this differs from HDD as
    defined in its original paper.
    """

    # Start with level 1 rather than 0 because 0 would mean attempting
    # to remove the entire input (the sole root node), which is very
    # unlikely to be accepted.
    level: int = 1

    nodes: list[TTNode] = nodes_at_level(root, level)

    while nodes is not empty and level <= max_passes:
      # Minimize and prune in one step.
      ddmin(nodes)

      level += 1
      nodes = nodes_at_level(root, level)

    # Note: Even without max_passes, we might have stopped before
    # `level` hit MAX_DEPTH since deep nodes might have been pruned.

The max_passes check is only active if --max-passes was specified.


Deviations from Original HDD
----------------------------

Things that make smin's HDD worse:

HDD replaces nodes with syntactically valid replacements depending on
context; for example, if it removes the condition of a `while` loop, it
substitutes "(0)".  smin is deliberately less aware of the language
rules, and its replacement possibilities are currently limited to either
the empty string or, for brace-delimited nodes, a single semicolon (in
addition to the empty string).

Things that make smin's HDD better (on the inputs I care about):

HDD says it uses ddmin as described in Zeller and Hildebrandt 2002,
which includes testing of candidates that *only* contain a given run
(which ZH2002 calls "reduce to subset"), whereas this specification
omits that, and creates candidates only by *removing* runs ("reduce to
complement").  This is motivated by the observation that, in practice,
when using the `delta` implementation of ddmin, the run-only candidates
are overwhelmingly rejected, making them a waste of time despite being
comparatively cheap.

ddmin also continues until it reaches 1-minimality at each granularity
("continue reducing $\Nabla_i$ with $n-1$ subsets"), whereas the
approximation specified here makes a single pass at each granularity.
That choice is motivated the observation that the inputs I am interested
in have dependency edges that almost exclusively run from a reference
later in the file to a declaration earlier in the file, and therefore
removing something earlier in the file can almost never enable removal
of something later.


Progress report
---------------

The progress report fields are as follows:

  P:  level
  Pm: MAX_DEPTH, capped by --max-passes
  G:  G
  F:  <see next>
  R:  number of live tokens replaced by candidate

F, the completion fraction for a given `ddmin` pass, is calculated as
the candidate number C divided by the maximum number Cm of candidates,
where Cm ignores tests with non-trivial replacements.

For example, if `nodes` contains 4 elements [1,2,3,4], and no candidate
were accepted, and we ignore non-trivial replacements, the tested
candidates would have retained nodes:

  At G=2:
    [1,2]          # Try removing [3,4] first.
    [3,4]
  At G=1:
    [1,2,3]
    [1,2,4]
    [1,3,4]
    [2,3,4]

Thus, Cm = 6, and we number the candidates 0 through 5 (so F is always
less than 1).

When we do try a non-trivial replacement, it uses the C from its
trivial replacement candidate, plus 0.5.

As the `ddmin` algorithm runs, C reflects where the candidate is in
relation to the original complete list of possible candidates, meaning
it potentially jumps forward when G changes.

We can calculate Cm and the starting C for each iteration with a loop:

  def compute_candidate_numbers(n: int) -> tuple[int, dict[int, int]]:
    """
    Return Cm for a `ddmin` pass whose input is a list of length `n`,
    and a map from G to the C for that iteration's starting candidate
    number.
    """
    C: int = 0
    C_for_G: dict[int, int] = {}

    # Start G the same way `ddmin` does.
    G: int = max(1, n // 2)

    while G > 0:
      # Candidate number at the start of pass with granularity G.
      C_for_G[G] = C

      # Number of candidates we would test if (1) all were rejected and
      # (2) no non-trivial replacements were tried.
      C += ceil(n / G)

      # Reduce the granularity the same way `ddmin` does.
      G //= 2

    return C, C_for_G

Call this at the start of `ddmin` and use its results to feed into the
progress report.


Enablement
----------

This algorithm is enabled by passing --hdd to smin.py.
